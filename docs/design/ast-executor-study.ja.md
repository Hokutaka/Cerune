# Source / AST直接実行経路の調査

[English](ast-executor-study.en.md)

調査対象：PR #75を統合した `9214509`（2026-09-30）。**調査上の推奨は、現時点ではAST Executorを採用せず、機能追加の必須前提にも置かないことです。** 実装不能という判断ではありません。新しい実行境界として得られる検証価値に対し、型・展開・所有・出自の二重管理が大きいためです。本メモは実装の承認や仕様の確定ではありません。

IR Executorの現行機能対応と検証は完了し、masterへ統合済みです。この調査で実行器・frontend・言語仕様を変更していません。

## 「Sourceから実行」と「ASTを実行」を分ける

`run-ir file.ceru`はすでにソースを入力できますが、実行するのは完成済みCerune IRです。ソース入力の窓口を増やして同じIR Executorへ渡しても、独立したAST実行経路にはなりません。

AST Executorという場合、少なくとも次のどれを直接辿るかを決める必要があります。

| 候補の入力 | 得られる比較 | 主な負担 |
| --- | --- | --- |
| 構文解析直後のAST | generic・match・配列反復などの展開前後を比較できる可能性 | 確定型・参照先・定数値が不足。元構文の実行意味を別途扱う |
| 共通展開後のAST＋意味解析情報 | ASTから型付きIRを作る境界の比較 | 式ごとの確定情報、所有処理、IRとの出自対応が未整備 |
| 共通展開・所有処理をすべて反映した表現 | 既存の基準実行と重なる | 現在の完成済みIRがこの役割を担っている |

比較の順序は「AST実行結果 → IR Executorへ入力」という実行パイプラインではありません。同じソースから異なる段階で分岐する実行結果の比較です。

## 現在のASTにある情報・ない情報

[ast.rs](../../src/ast.rs)の`Expr`・`Stmt`は`kind`と`Span`を持ちます。演算子、引数・フィールドの記述順、制御構造、型注記、整数の数字列と接尾辞、浮動小数点の本文と任意の接尾辞、復号済み文字列を保持しています。型参照は名前や配列形、未解決の定数長を表します。enum、match、generic呼び出し、配列反復の構文もあります。

一方で、全式の確定型、各変数参照のBindingId、全ノードのNodeId、確定した呼び出し先・フィールドID、凍結済み定数値、保持・解放命令はASTの各要素に付いていません。コメント・空白・文字列エスケープの元の綴りまで完全に再現する構文木でもありません。正確な元テキストはSourceMapが保持します。

`compile(source)`は検査を行った後も元のASTを返します。「検査済み」であることと「実行に必要な確定情報をASTに注釈済み」であることは別です。

[SemanticModel](../../src/semantic.rs)には型・フィールド・関数の定義とID、定数の型、束縛情報、型問い合わせAPIがあります。元ASTのgeneric呼び出しの型を問い合わせる対応もあり、共有の足場はあります。ただし、各スコープ内の全式・全参照に対する確定結果を保存した実行用の表ではありません。`analyze`が内部で作った展開済みASTも返しません。型問い合わせには可視な束縛や期待型が必要です。

例えば`x: f32 = 0.1 + 0.2;`の式を期待型なしで評価すると、接尾辞なしのfloatをf64へ決めてしまいます。型規則は共有できても、正しい文脈を渡す処理は必要です。また、到達しない分岐も現行ルールに従って事前検査する必要があり、実行時に通った枝だけ検査する方式にはできません。

## IR構築までの処理とAST実行への影響

以下は主な依存関係です。定数長の解決は必要な定数のIR構築を呼ぶため、すべてが一度だけ直線的に流れるわけではありません。

| 処理・現在の場所 | 現在確定する意味 | AST経路での共有と障壁 |
| --- | --- | --- |
| [モジュール読込・解決](../../src/modules/resolve.rs) | import、pub、名前の衝突、依存先の名前を共通ASTへ解決 | 再利用可能。ただし読込後のASTはファイルごとの原形そのものではない |
| [generic展開](../../src/generics.rs) | 明示した型・長さへの具体化と出自 | AST変換を再利用できる。再利用すると具体化そのものの独立検証にはならない |
| [配列型の定数長](../../src/array_lengths.rs) | 依存・循環・正の長さ・使用位置 | 必要な定数を既存IR構築経由で評価する。独立したASTだけで完結する工程ではない |
| [enum / match展開](../../src/sums.rs) | タグ・ペイロード、網羅性、ガード、束縛、Let/Conditional | AST変換を共有可能。元のmatchを直接実行するなら分岐とコピーの実行意味が別途必要 |
| [意味解析](../../src/semantic.rs) | 型、可視性、mut、呼び出し、再帰の制限等 | 規則は共有できるが、元ASTに全結果を保存するAPIではない |
| [IR builder](../../src/ir/builder.rs) | 文脈型、BindingId/NodeId、参照先、組み込み操作、既定フィールドの評価順 | 確定結果の保持と構築が結び付いている。ASTにも同じ情報を必要とするなら共通処理の切り出しが必要 |
| [配列反復](../../src/iteration.rs) | 一度だけの配列コピー、添字付きfor、continue時の更新 | builder内から呼ぶAST展開を共有可能。元のfor-inを直接実行するならこの契約を実行器側でも保つ |
| [定数評価](../../src/ir/builder/constants.rs) | 評価・失敗の診断・静的値への凍結 | 現在はIR → Bytecode → VM。再利用する場合、このコンパイル時依存を明示する必要がある |
| [複合値の共通展開](../../src/ir/aggregates.rs) | 比較・表示・match由来の式をコピー、関数、ループへ展開 | 入出力がIR。ASTへそのまま適用できない |
| [所有の共通展開](../../src/ir/ownership.rs) | 引数・戻り値・一時値・スコープ・分岐での保持と解放 | 入出力がIR。AST実行器のRust値をdropするだけでは同じ契約にならない |

構造体の構築でも、元の値、明示フィールドのソース順、省略した既定値の定義順を守る必要があります。型定義のフィールド順だけで評価する実装では、副作用や失敗順が変わります。

### 所有と出自が特に難しい理由

文字列の予算は単なる実装内部の都合ではありません。同じソース・同じ予算での成功／失敗が観測されます。`saved = s`のコピー、`s = concat(s, "c")`の旧新の共存、matchの一時コピー、return/break/continueでの回収時点が一致する必要があります。

[runtime/string_heap.rs](../../src/runtime/string_heap.rs)の共有は可能ですが、いつretain/releaseするかは現在IRの所有パスが決めています。AST側に別の寿命規則を作ると、表示が一致しても小さい予算で失敗位置が変わり得ます。GCやRustの参照数をそのまま基準にするだけでは、現行の生存バイト数の意味を保てません。

ASTのSpanは診断位置に使えますが、IRのNodeIdと同一ではありません。同じSpanからgenericの複数具体化や複数の生成処理が生まれます。Spanだけでノードを一意に対応付けたり、比較のためだけにIRを生成して番号を転用したりしても、独立した由来の契約にはなりません。将来比較する場合は、ソース要素・具体化・生成要素との対応を別途定義する必要があります。

## frontend semanticsを二重実装せず共有できるか

**部分的には可能ですが、現在のAPIを呼び出すだけで全機能のAST実行器を自然に足せる状態ではありません。**

モジュール解決、generic・sum・配列反復のAST変換、型・数値変換・文字列領域管理は共有候補です。しかし、確定したASTと対応する意味情報・定数値・出自を一つの成果として受け取る境界はなく、所有と複合値展開はIRを入力にします。

将来必要になれば、まず既存のfrontendから「同じASTに対応する確定情報」を一度だけ取り出す整理を検討できます。ただしAST実行のためだけに、既存IRとほぼ同内容の第二の型付き表現を設けることは推奨しません。また、IRを構築してIR Executorに実行を委譲するものをAST Executorと呼びません。定数評価のようなコンパイル時の共有とは区別します。

## 段階比較の価値と限界

- **価値がある場合**：元のmatch・for-in・構築式を実行し、展開後と比較することで、IR以前の変換による評価順・コピー・分岐の誤りを発見できる。
- **共有するほど狭まる独立性**：同じgeneric/match/ownership展開を通れば、その展開の誤りは両経路に共通して残る。AST Executorがあるだけでfrontend全体の独立した正解にはならない。
- **今ある比較の範囲**：IR Executor・VM・compiled routesの比較は、主に完成済みIR以降の実装差を検証する。frontend自体は既知の期待値、コンパイル失敗、IRの形と出自のテストで検証する。
- **性能比較**：解析・展開・型解決と実行を分け、同じ事前処理・出力・予算条件を記録する。AST側だけ実行中に型問い合わせを繰り返す測定は、走査方式だけの比較ではない。今回は測定しておらず、速度の優劣は判断しない。

既存の検証には[IR実行比較](../../tests/ir_executor.rs)、[観測fixture](../../tests/observation_cli.rs)、[generic](../../tests/generic_functions.rs)、[sum](../../tests/sums.rs)、[複合値](../../tests/aggregate_values.rs)、[配列反復](../../tests/array_iteration.rs)、[所有予算](../../tests/string_heap_routes.rs)があります。特に、短絡して実行しないgeneric呼び出しの型エラー、反復開始時のコピー、先行出力と失敗した式、小さい予算での寿命を既知の契約と照合します。

## emit-sourcesとの違い

| 操作 | 観測・実行するもの |
| --- | --- |
| `emit-sources` | `cerune-sources-v1`のファイルID・名前・正確な本文。AST・確定型・実行状態ではない |
| AST観測（候補、未実装） | 構文の木と展開前後・解決結果・出自の対応。プログラムを実行する必要はない |
| AST Executor（今回不採用を推奨） | 特定段階のASTに基づく計算・状態・出力・実行時停止 |
| `emit-ir` / `run-ir` | 完成済みIRの観測／直接実行 |

[現在のCLI](../../src/main.rs)の`emit-sources`は共通IR構築の検証後にmanifestを出力します。実行器を呼ばず、トップレベルのprintやmainは実行しません。ただし定数評価などのコンパイル処理はあり、単なる無検証のファイルコピーでもありません。

実物も`examples/modules/main.ceru`で確認しました。`emit-sources`は入口とvalues.ceruの2ファイルのID・名前・本文、`emit-ir`は解決後の型と関数、既定フィールドの式、NodeIdを出力します。

## 推奨する次の進め方

1. IR Executorを完成済みIRの基準経路として維持し、新機能も既知の期待値・各経路との比較対象にする。
2. 生成過程の見通しを改善するなら、実行経路を増やす前に、既存frontendの変換前後と出自の読み取り専用観測を検討する。安定IDや公開スキーマは必要な観測内容を定めてから設計する。`emit-ast`等のコマンド名もまだ確定しない。
3. AST実行は、特定のfrontend変換を独立比較する必要や教育・デバッグ上の具体的用途が出た時点で再検討する。その際は共有する意味処理、独立に検証する変換、所有予算と出自の一致条件を先に決める。

今回、新しいAST・HIR・共通実行器の抽象化は追加しません。IR Executorに未展開ASTの受け入れや所有処理の切り替えを持ち込まず、設計を維持します。動的配列等の機能追加は、AST Executor完成を待つ必要はありません。
